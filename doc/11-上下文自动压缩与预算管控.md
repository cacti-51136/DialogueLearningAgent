# 11 · 上下文自动压缩与预算管控

> 本篇是 [01 · 架构设计总览](./01-架构设计总览.md) 的**补充子系统**，解决一个此前未覆盖的异常场景：
> **当整窗上下文（含 System Prompt + 历轮摘要链 + 冷记忆 + 工具 schema + 当前消息）总量即将占满模型上下文窗口时，自动触发一次 compact 操作**，把上下文瘦身到安全水位以下，避免静默截断、报错或成本失控。

## 0. 背景与缺口

### 0.1 已有的预算机制（不够用）
- **`prompt/budget.py`（doc/01 §5 / doc/02 §7.1）**：对 **L1/L2/L3 权重段**做"分层 Token 预算 + 按权重降序裁剪"，总盘子 `DLA_PROMPT__TOTAL_TOKEN_BUDGET=900`。它管的是"**权重 Prompt 这一段**"别爆。
- **`DLA_MEMORY__PROMPT_RATIO=0.15`（doc/07 §4.4）**：冷记忆注入占独立子预算，超了按相似度裁剪。
- **`turn_summary` 链（doc/07 §4.6）**：下一轮默认注入的历史 = 历轮 ≤100 字摘要拼接，而非完整原文。

### 0.2 仍然缺失的环节
这些机制都**假设"其它部分不会无限增长"**，但事实相反：
1. **`turn_summary` 链是线性增长的**：每轮 +1 条，长会话（如 200 轮）累积 ~200×100 字，最终撑爆窗口——而 doc/07 只把"跨会话冷库"做了周期性压缩（节点 ⑤ `maybe_compact`），**对"活跃注入链"没有任何压缩**。
2. **`detail_blocks`（召回原文片段）**：虽是单轮瞬态，但若连续多轮触发 `recall_memory`，会反复堆积进当前上下文。
3. **工具 schema**：插件越多，全量 schema 注入越大（doc/08 两级路由虽控制"选哪个"，但未控制"注入多大"）。

> 结论：**缺一个"整窗占满 → 主动 compact"的护栏**。本篇补上它。

---

## 1. 设计目标

1. **预算感知**：每轮组装 Prompt 完成后、调用 LLM 前，估算**整窗** token 占用。
2. **主动触发**：占比达阈值即触发压缩，**不等到真正溢出报错**才补救。
3. **无损 / 低损可控**：压缩只移除"已持久化、可恢复"的内容，或对历史做"有损但可 recall"的合并；绝不丢弃未落盘的信息。
4. **可观测、可回滚、可手动**：每次压缩记录前后 token 数、动作、原因；支持 `dla ctx status/compact`。
5. **与既有架构兼容**：复用 doc/02 分层预算 + doc/07 冷热记忆，不改动权重引擎与记忆存储本身。

## 2. 上下文预算模型

### 2.1 两个预算，不要混淆
| 预算 | 含义 | 配置 |
|---|---|---|
| **权重段预算** | 仅 L1/L2/L3 渲染出的那段 Prompt | `DLA_PROMPT__TOTAL_TOKEN_BUDGET=900`（doc/01 §8） |
| **全窗预算（本篇）** | 模型上下文窗口的总可用输入 token | `DLA_CTX__MAX_TOKENS`（本篇，默认按所用模型，如 128000） |

本篇监控的是**后者**——它包权重段、摘要链、冷记忆、工具 schema、当前消息等一切。

### 2.2 预算公式
```
RESERVE      = DLA_CTX__RESERVE            # 安全储备，留给输出生成（默认 0.20）
budget_in    = MAX_TOKENS × (1 - RESERVE)
estimated    = Σ part_tokens(                # 每轮组装后实估
                   system_weight_prompt,
                   turn_summary_chain,        # 增长最快的部分
                   cold_context,             # 受 PROMPT_RATIO 约束
                   detail_blocks,            # 本轮瞬态
                   tool_schemas,             # 随插件数增长
                   current_messages,
                   output_reserve)
fill_ratio   = estimated / budget_in
```

### 2.3 Token 估算策略（可配 `DLA_CTX__TOKENIZER`）
- **`deterministic`（默认，零依赖）**：中英文混合场景下 `tokens ≈ Σ len(seg) / CHAR_PER_TOKEN`，取 `CHAR_PER_TOKEN=2.6`（CJK ~1.6 字/词、EN ~4 字/词加权）。与 doc/06 零依赖哲学一致，保证不联网可测。
- **`tiktoken`**：精确，需安装。
- **`api`**：调用模型 `count_tokens`（若 provider 支持）。

> 默认 `deterministic` 已足够驱动阈值判断；精确计费场景可切 `tiktoken`。

## 3. 触发阈值（阶梯）

| 级别 | 阈值 | 动作 |
|---|---|---|
| `WARN` | `DLA_CTX__WARN_RATIO=0.70` | 记 warn 日志 + 调试帧提示，**不压缩** |
| `COMPACT` | `DLA_CTX__COMPACT_RATIO=0.85` | 触发**自动压缩协议**（见 §4） |
| `HARD` | `DLA_CTX__HARD_RATIO=0.95` | 压缩后仍超则**升级处理**（强制合并 + 必要时丢弃最旧 epoch 摘要 + 用户提示） |

**触发时机**：在 doc/01 §7 数据流 **step 7（组装 Prompt）之后、step 8（调用 LLM）之前**，插入：

> **`7½. 预算护栏 budget_guard`**：组装完成后估算 `fill_ratio` → 若 ≥ `COMPACT` 则运行 compact 协议 → 重新估算，直到 < `COMPACT` 或资源耗尽（已达 HARD 升级路径）。

doc/07 LangGraph 图中对应新增节点 **⑦ `budget_guard`**（位于 ② `prepare_prompt` 与 ③ `generate` 之间）。

## 4. 压缩协议（compact protocol）

按"**信息损失最小优先**"的顺序执行动作，每步后重估 `fill_ratio`，**达标即停**，不盲目执行全部动作。

| # | 动作 | 信息损失 | 说明 |
|---|---|---|---|
| 1 | **驱逐瞬态 `detail_blocks`**（若当前轮未引用） | 零（已落盘冷库，可 recall） | 工具取回的原文片段本就只进当前轮；未引用即删 |
| 2 | **合并 `turn_summary` 为 `epoch` 摘要** | 低（原文留冷库） | 见 §4.1 |
| 3 | **裁剪冷记忆注入** | 低（按需可召回） | `cold_context` 按相似度降序仅保留 top-M，M 随 fill 动态缩小 |
| 4 | **精简 L2/L3 表述** | 极低（仅展示详尽度） | 对低 salience 维度仅保留"标签+值"，省略自然语言解释句；下一轮按权重重建时恢复 |
| 5 | **工具 schema 极简模式** | 无（能力不丢） | fill 高时只注入 `name+description`，省略参数 schema；或仅注入路由 top-N 工具（依赖 doc/08 路由） |
| 6 | **（HARD 级）丢弃最旧 `epoch` 摘要** | 中（信息已在冷库，可恢复） | 仍超 HARD 则丢弃最旧 epoch 摘要，并向用户提示"较早的对话上下文已被精简" |

### 4.1 epoch 摘要合并（核心动作）
- 当 `turn_summaries` 链长度 > `DLA_CTX__SUMMARY_COMPACT_AFTER`（默认 **40**），或预算触发时，将**最旧 N 条**（默认 N=10，`DLA_CTX__EPOCH_MERGE_N`）经 LLM 合并为 **1 条 `epoch_summary`**（≤ `DLA_CTX__EPOCH_MAX_CHARS` 200 字），保留主线。
- 压缩比约 **N:1（默认 10:1）**；epoch 摘要本身可**递归再合并**为 super-epoch。
- **原逐轮 summary 与原文仍存于冷记忆**，合并仅在"活跃注入链"上发生——信息不丢失，`recall_memory` 仍可取回细节。
- 离线兜底：若 LLM 不可用（单测），用模板合并（首尾句 + 关键词提取）生成 epoch 摘要。

### 4.2 关键不变式（Invariant）
> **被从活跃上下文移除的内容，必须已持久化于冷记忆（可由 `recall_memory` 重新取回），或仅是本轮瞬态 `detail_blocks`。**
> 绝不丢弃未落盘的内容；**压缩绝不动 L1/L2/L3 的权重数值**，只调整它们的"表述详尽度"。

## 5. 与 doc/07 的关系（两处"compact"之别）

| | doc/07 节点 ⑤ `maybe_compact` | **本篇 ⑦ `budget_guard`** |
|---|---|---|
| 对象 | **冷记忆库**（长期存储） | **当前上下文窗口**（单轮活跃注入） |
| 触发 | 周期性（每 `COMPACT_EVERY_N_SESSIONS`） | **实时**：预算占比达阈值 |
| 目的 | 控制冷库规模、降噪 | 防止单轮上下文溢出 |
| 频率 | 跨会话、低频 | 单会话、按需 |

二者**互补**：⑤ 管"长期存储规模"，⑦ 管"单轮窗口占用"。

---

## 6. 安全防护

| 护栏 | 说明 |
|---|---|
| 无损优先 | 动作 1/2/3 均不丢可恢复信息；动作 2 仅发生在活跃链、原文留冷库 |
| 不静默改权重 | 压缩绝不动 L1/L2/L3 权重值，只动"表述详尽度" |
| 不抛栈 | 压缩协议异常则跳过、记 warn、继续用当前上下文生成 |
| 可观测 | 每次压缩写 `context_compact_log`（doc/03 §2.17）+ 调试帧 ⑪（doc/04 §2.3） |
| 手动覆盖 | `dla ctx status` 查看占比；`dla ctx compact [--force]` 手动触发 |
| 可关 | `DLA_CTX__AUTO_COMPACT=false` 关闭自动触发（仍可手动触发） |

## 7. 配置与环境变量（接入 doc/01 §8）

```bash
# ---- 上下文自动压缩（doc/11）----
DLA_CTX__MAX_TOKENS=128000            # 模型上下文窗口（按所用模型配置）
DLA_CTX__RESERVE=0.20                 # 安全储备比例（留给输出生成）
DLA_CTX__TOKENIZER=deterministic      # deterministic | tiktoken | api（估算策略）
DLA_CTX__WARN_RATIO=0.70              # 占比告警阈值
DLA_CTX__COMPACT_RATIO=0.85           # 触发自动压缩阈值
DLA_CTX__HARD_RATIO=0.95              # 硬上限阈值（压缩后仍超则升级处理）
DLA_CTX__AUTO_COMPACT=true            # 默认开；false=仅手动触发
DLA_CTX__SUMMARY_COMPACT_AFTER=40     # turn_summary 链超过此条数即参与合并
DLA_CTX__EPOCH_MERGE_N=10             # 每多少条 summary 合并为 1 条 epoch 摘要
DLA_CTX__EPOCH_MAX_CHARS=200          # epoch 摘要硬上限
DLA_CTX__COLD_TRIM_TOP_M=2            # 高压下冷记忆注入保留条数下限（动态再缩）
```

## 8. 存储（接入 doc/03 §2.17）

### 8.1 `context_compact_log` 表
记录每次压缩事件，供回放 / 调试：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| session_id | TEXT | |
| turn | INTEGER | 触发轮次 |
| trigger_level | TEXT | WARN / COMPACT / HARD |
| fill_before | REAL | 压缩前占比 |
| fill_after | REAL | 压缩后占比 |
| tokens_before | INTEGER | 压缩前估算 token |
| tokens_after | INTEGER | 压缩后估算 token |
| actions | TEXT(JSON) | 实际执行的动作序列 |
| epoch_summary_id | TEXT? | 若本轮回生成了 epoch 摘要，记录其 id |
| created_at | TIMESTAMP | |

### 8.2 `epoch` 摘要的存法（不新建表）
`epoch_summary` **作为 `turn_summaries` 链中的特殊项**存储：`kind='epoch'`（逐轮项为 `kind='turn'`）。渲染时二者同链展示，但合并逻辑只对 `kind='turn'` 的连续块生效，且原始逐轮 summary 在冷记忆中始终保留全量。对应新增 `ContextCompactRepository`（doc/03 §3）。

## 11. 测试策略

| 层 | 范围 | 用什么 |
|---|---|---|
| 单测 | `ContextBudgetMonitor.estimate` 在 deterministic 下估算稳定；compact 协议按动作顺序降 token，且不丢未落盘内容 | 假 tokenizer + 内存 store |
| 集成 | 构造 200 轮 summary 链，断言 fill 超 `COMPACT` 后自动触发合并、生成 epoch 摘要、fill 回落 < `COMPACT`；断言冷库仍含原始 summary | 假 LLM + 假 embedding + 真实 SQLite |
| 护栏 | compact 函数抛异常时，断言不抛栈、仍用当前上下文正常生成 | mock 抛错 |

**核心断言**：长会话（≥200 轮）下，开启 `AUTO_COMPACT=true` 时，单轮组装后 `fill_ratio` 始终被压在 `COMPACT` 以下，且任意历史细节仍可经 `recall_memory` 取回。
