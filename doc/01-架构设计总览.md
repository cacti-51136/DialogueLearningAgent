# 01 · 架构设计总览

## 1. 目标与非目标

### 1.1 本期目标

| 编号 | 目标 | 验收方式 |
|---|---|---|
| G1 | 建立三层关键词（场景 / 用户 / Agent）的统一权重模型 | 纯函数单测，无需联网即可验证 |
| G2 | 对话过程中自动分析并增量更新用户肖像 | 脚本化剧本回放，断言权重演化方向 |
| G3 | 由 L1 × L2 推导出当轮 Agent 人格并组装 System Prompt | 给定输入可复现同一 Prompt |
| G4 | 人格切换平滑，不出现"人设跳变" | 滞回阈值 + 冷却轮次，有审计记录 |
| G5 | 通过 CLI 完成完整对话闭环，且能解释"为什么这么回" | `dla chat --explain` 打印三层权重 |
| G6 | PyQt 界面可实时对话，并可视化三层权重演化 | 手动冒烟 + 长对话不卡顿 |

### 1.1.1 对话与界面语言约定

- **默认中文，但中英混合是自然允许的**。用户可以中文夹杂英文术语（如"这个 token 有点问题"），Agent 也应在保持中文主体的同时自然保留必要的英文专业词，而不是强行翻译或拒绝。
- 语言**靠场景模板与约束维度引导，不靠硬编码 if 判断**。例如语言学习场景用 `constraint.english_only` 维度去促成英文沉浸，日常场景则放松。框架层不写"如果语言==中文则…"。
- 词库、UI 文案、给 LLM 的判定说明（keyword 的 `description`）一律中文，方便后续开源社区贡献。

### 1.2 明确不做（避免范围蔓延）

- 不做多用户账号体系 / 权限 / 云端同步。首期为**单机单用户**，但数据模型预留 `user_id` 字段。
- 不做**对话历史**的向量检索 / RAG / 语义搜索。关键词本身就是显式的、可解释的记忆表示，这是本项目的设计取舍。**但本项目的"词库"本身会被向量化**（见 [06 · 向量化词库与在线学习](./06-向量化词库与在线学习.md)）——那是把**关键词**编码为向量、用可训练关联矩阵建模"场景↔用户↔Agent"的跨层关系，与"检索聊天记录"是两回事，不属于此处排除的 RAG。
- 不做**大模型微调**。人格调节全部通过 Prompt 实现；被训练的只有一个很小的**本地关联模型**（d×d 双线性矩阵，纯 numpy），而非 LLM 权重。
- 不做语音输入输出。
- 不引入消息队列与独立任务进程。后台分析在进程内的受控异步中完成即可，任务量远未到需要 Celery 的程度。

## 2. 术语表

| 术语 | 含义 |
|---|---|
| **关键词（Keyword）** | 一个带语义的原子标签，如 `mood.frustrated`、`tone.encouraging`。分**类别型**与**程度型**两种。 |
| **类别型 / categorical** | 互斥选项，取且仅取一个，如 `role` ∈ {外教, 同事, 朋友}。按权重取 argmax。 |
| **程度型 / scalar** | 连续值，归一化到 `[0,1]`，如 `empathy=0.8`、`verbosity=0.3`。按权重加权平均。 |
| **维度（Dimension）** | 同类关键词归为一个维度，维度内做归一化与冲突消解。 |
| **权重（Weight）** | 该关键词对最终 Prompt 的影响力，见 [02 文档](./02-三层关键词权重模型.md)。 |
| **置信度（Confidence）** | 我们对这条判断有多大把握，与"权重"是两个独立概念。 |
| **证据（Evidence）** | 支撑某条用户肖像判断的原始观测，带强度与时间戳，是置信度的来源。 |
| **快照（Snapshot）** | 某一轮次三层权重的完整存档，用于可视化与离线调参。 |

## 3. 技术选型

| 层面 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.13 | 与 LLM/数据生态一致，团队无跨语言成本 |
| LLM 接入 | `openai` SDK + 可配 `base_url` | 一套代码适配 OpenAI / DeepSeek / 通义 / 本地网关，切换只改环境变量 |
| 结构化输出 | JSON Schema 约束 + 白名单校验 | 关键词必须是受控词表内的，绝不允许模型自由发挥造词 |
| 存储 | SQLite（标准库 `sqlite3`） | 零运维、单文件、本地场景够用；仓储层抽象后可换 PostgreSQL |
| 迁移 | 自建 migration runner | Schema 简单，引入 Alembic 收益不足以抵消依赖成本 |
| 配置 | `pydantic-settings` + `.env` | 启动时集中校验、快速失败 |
| CLI | `typer` + `rich` | 声明式参数，表格/树形输出开箱即用 |
| 桌面 UI | **PyQt6**（经 `qt_compat` 抽象） | 见下方许可证说明 |
| 日志 | `structlog` 风格 JSON 输出 | 便于后续排查与离线分析 |
| 测试 | `pytest` + `pytest-cov` | 权重引擎为纯函数，单测覆盖率目标 ≥ 85% |
| 质量 | `ruff` + `mypy` | 核心引擎强制类型标注 |

### 3.1 关于 Qt 绑定与许可证

**已确认本项目未来必定开源。** 这直接消解了之前最大的许可证风险：PyQt6 采用 **GPLv3 / 商业双许可**，而 GPLv3 与开源分发完全兼容——只要按 GPLv3 发布（保留版权与许可声明、提供源码），使用 PyQt6 没有任何合规障碍，无需购买商业许可，也无需切到 PySide6。

**决策**：默认使用 PyQt6（GPLv3），按开源协议发布。尽管如此，所有 Qt 导入仍经过 `src/dla/ui/qt/qt_compat.py` 这一层：

```python
# qt_compat.py —— 切换绑定只需改这一个文件
try:
    from PyQt6.QtCore import QObject, QThread, pyqtSignal as Signal
    from PyQt6.QtWidgets import QApplication, QMainWindow
except ImportError:
    from PySide6.QtCore import QObject, QThread, Signal
    from PySide6.QtWidgets import QApplication, QMainWindow
```

这层抽象的成本接近零，但保留了将来切换绑定（例如出于打包体积或上游支持考虑）的灵活性。

## 4. 分层架构

整体遵循**按功能组织 + 三层架构**，核心原则：**控制器不写业务逻辑，核心引擎不依赖任何 UI 框架**。

```

│  ┌──────────┐   ┌──────────────┐   ┌──────────────────┐    │
```

## 6. 关键设计决策

每条一句话说明取舍：

| # | 决策 | 理由 |
|---|---|---|
| D1 | 关键词分**类别型 / 程度型**两类 | 纯互斥标签会导致硬冲突（"简洁"vs"详尽"）；程度型用连续值加权平均，天然可共存 |
| D2 | L2 的预设项与观察项**共用同一套证据公式** | 预设项反推一个等效初始证据强度即可统一，代码路径唯一，避免两套逻辑漂移 |
| D3 | L3 **不直接接受用户输入**，只由 L1×L2 推导 | 保证人格始终服务于场景与用户，而不是随机设定 |
| D4 | 耦合规则默认走**确定性规则**，LLM 精炼可选且融合权重可配 | 规则可解释、零延迟、零成本；LLM 兜住规则覆盖不到的长尾，β 默认 0.3 |
| D5 | Prompt 采用**分层 Token 预算 + 按权重降序裁剪** | 防止长对话后关键词无限膨胀挤爆上下文 |
| D6 | 人格重建引入**滞回阈值 + 冷却轮次** | 避免用户一句话就让人格翻天覆地，产生"精神病"观感 |
| D7 | 分析器**不是每轮都调 LLM** | 成本与延迟控制；冷启动强制 + 周期 + 启发式事件触发三者结合 |
| D8 | 核心引擎提供**同步 / 异步双入口** | Qt 侧用同步 + QThread（最稳，避免与 asyncio 事件循环打架），CLI 与 API 用异步流式 |
| D9 | 存储用标准库 `sqlite3` + 自建迁移 | 依赖最小化；Repository 抽象保留替换空间 |
| D10 | 每轮保存**权重快照与 L3 变更审计** | 这是本项目的可观测性核心，也是后续调参的数据基础 |
| D11 | 关键词必须命中**白名单词表** | 模型自由造词会导致词库爆炸、权重稀释，一律丢弃非法词并记日志 |
| D12 | 分析失败**静默降级**，绝不中断对话 | 分析是增强项不是必需项；失败时沿用上一轮权重 |
| D13 | **词库随对话自动演化**，新增/调整词的判定交由 LLM | 用户/领域语言不可枚举，封闭词表会随时间僵化；LLM 负责"该不该收编这个新概念"的判定，人工审核兜底 |
| D14 | **默认中文、中英混合**；语言靠场景模板引导而非硬编码判断 | 真实对话天然夹杂术语；用 constraint 维度引导语言，不写死 if 语言==中文 |
| D15 | **调试模式输出完整思维链**（触发→抽取→规则→Δ→组装） | 可解释性是本项目内核，调试器要把"为什么这么回"拆解到人能逐帧看懂 |
| D16 | **词库向量化 + 在线学习**：关键词编码为 d 维向量，跨层关联用可训练双线性矩阵 `M_r` 表示；`M_r` 按学习率 + 损失函数（软交叉熵 + 排序边界 + 权重衰减）用解析梯度更新 | 关联可学习、可计算，且完全离线、纯 numpy、无 GPU；LLM 不微调，只提供监督信号 |
| D17 | **LLM 实时增删改词库**：每轮分析额外产出 `agent_ops`（add/update/delete），作用于当前场景工作集，带护栏（基础词不可删、add 走审核、delta 有界） | 词库随对话自适应，但不失控；所有操作可审计可回放 |
| D18 | **双反馈回路**：前向（用户肖像丰富 → Agent 关键词贴合）+ 后向（满意度 → 反向调整 Agent 权重），共用同一 `M_r` | 最终效果：Agent 人格从场景模板默认值收敛到"这个用户、这种风格最满意"的定点 |

## 7. 一轮对话的完整数据流

```
用户消息进入
   │
   ├─ 0. 场景开始（冷启动，仅新会话）
   │      LVM 据初始 L1 权重生成 Agent 初始身份关键字（确定性、不调 LLM）
   │      —— 详见 [06 §3](./06-向量化词库与在线学习.md)
   │
   ├─ 1. 落库（messages 表，role=user）
   │
   ├─ 2. 触发判定 trigger.should_analyze(turn, message, state)
   │      ├─ 否 → 跳过分析，直接复用上一轮权重
   │      └─ 是 ↓
   │
   ├─ 3. 证据抽取
   │      ├─ heuristics.extract()          本地规则，零成本，同步
   │      └─ llm_analyzer.extract()        LLM 抽取，异步，带 JSON 校验
   │           → 合并 + 白名单词表过滤 + 强度裁剪 [0,1]
   │
   ├─ 4. 更新 L2
   │      E_t = Σ intensity_i × exp(-λ(t - t_i)) + E_preset
   │      conf = E_t / (E_t + K)
   │      w2   = base × conf × salience
   │
   ├─ 5. 重算 L3 = f(L1, L2)
   │      规则推导 → 可选 LLM 精炼 → 融合 → 维度归一化
   │
   ├─ 6. 稳定性判定
   │      Δ = 与上一轮 L3 的距离
   │      Δ < τ_rebuild → 沿用旧 Prompt（不重建）
   │      否则重建，Δ ≥ τ_notify 时向用户给出可见提示
   │
   ├─ 7. 组装 Prompt（预算裁剪 + 渲染）
   │
   ├─ 8. 调用 LLM 流式生成 → 逐 token 回调给交互层
   │
   ├─ 9. 落库：messages(role=agent) + weight_snapshots × 3 + persona_changes
   │
   ├─ 10. 返回本轮权重摘要（供 UI 渲染 / CLI --explain 打印）
   │
   └─ 11. 在线学习（LVM）
          依据本轮 `agent_ops` 与 `satisfaction` 构造监督信号（q_t → p*）
          对关联矩阵 M_r 做一步解析梯度更新（学习率 η、梯度裁剪、回放缓冲）
          写入 lvm_training_log 与检查点（M_r / 动量 / 步数）
          —— 详见 [06 §6](./06-向量化词库与在线学习.md)
```

## 8. 配置与环境变量

`.env.example` 仅含占位值，真实 `.env` 必须进 `.gitignore`，任何输出中不得出现真实密钥。

```bash
DLA_LLM__BASE_URL=https://api.openai.com/v1
```

## 9. 错误体系与降级策略

```python
class DlaError(Exception): ...            # 基类
class ConfigError(DlaError): ...          # 配置缺失/非法
class LexiconError(DlaError): ...         # 词库加载失败
class LlmError(DlaError): ...             # 上游调用失败（含子类）
class LlmRateLimitError(LlmError): ...
class LlmSchemaError(LlmError): ...       # 结构化输出不合规
class AnalysisError(DlaError): ...        # 分析流程异常
class StorageError(DlaError): ...
```

降级矩阵：

| 故障 | 处理 | 用户可见性 |
|---|---|---|
| 配置缺失 | 启动即失败，打印缺哪个变量 | 明确的启动错误 |
| 词库 YAML 非法 | 启动即失败，指出文件与行号 | 明确的启动错误 |
| LLM 分析超时/失败 | 重试 1 次后跳过本轮分析，沿用旧权重 | 无感（`--explain` 下可见） |
| LLM 输出非法 JSON | 尝试括号提取修复 → 失败则丢弃该批证据 | 无感 |
| 抽取到词表外关键词 | 丢弃 + 记 warn 日志（用于反哺词库） | 无感 |
| 主对话生成失败 | 重试 2 次（指数退避）→ 返回友好错误，不抛栈 | 明确的错误提示 |
| SQLite 写入失败 | 事务回滚，返回错误；对话本身不中断 | 提示"本轮未能保存" |

**通用原则**：客户端永远看不到堆栈、密钥、内部路径；日志不记录消息正文（除非显式开启 `DLA_LOG__LOG_CONTENT=true` 用于调试）。

## 10. 风险与权衡

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| LLM 抽取的关键词不稳定，同类表述给出不同词 | 权重抖动 | 白名单词表 + 同义词归一 + 半衰期平滑 + 冷却轮次 |
| 长对话后证据堆积，老印象洗不掉 | 用户画像僵化 | 指数衰减 + 提供 `dla portrait reset --soft` 软重置 |
| Prompt 过长导致成本上升 | 费用与延迟 | 分层预算硬裁剪 + 每轮快照监控 token 数 |
| 规则与 LLM 精炼结论打架 | 人格不一致 | β 融合 + 分歧超阈值时以规则为准并记日志 |
| PyQt 许可证合规 | 法律风险 | `qt_compat` 抽象层，可低成本切 PySide6 |
| 权重参数凭感觉调，缺乏依据 | 效果调优困难 | `dla bench` 剧本回放 + 快照数据离线分析 |
